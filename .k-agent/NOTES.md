# Workspace notes

- RE toolchain is user-local: Ghidra in `~/tools/ghidra_12.1.4_PUBLIC` (pinned, the GhidraMCP 2.0 extension is built for it), jadx in `~/tools/jadx-1.5.6`, Android SDK in `~/Android/Sdk`, CLI tools in `~/.local/bin`. Load it with `. tools/env.sh`. jadx takes the heap through `JADX_OPTS=-Xmx6g`, and a long decompile runs in a docker container so it survives the session. MobSF runs in the container `mobsf` on `127.0.0.1:8000` (restart with `docker start mobsf`): upload, scan, then poll `report_json` with the hash.
- The host default is JDK 26, which gradle cannot use (the kotlin dsl cannot parse "26.0.1"). Build the apk with `JAVA_HOME=$HOME/.jabba/jdk/openjdk@21.0.2` and `ANDROID_HOME=$HOME/Android/Sdk`, then `./android/gradlew -p android assembleRelease`. The docker apk build caches gradle in the named volume `k-tvs-connect-gradle`, seeded from `~/.gradle`; mounting `~/.gradle` directly breaks the gradle daemon.
- The phone is connected over usb as RCUSTSEQTSK7RKSW (model 2602DPT53G). The MIUI phone can revoke INJECT_EVENTS for the adb shell, then `adb shell input tap` fails with exit 255; unlock it and enable "USB debugging (Security settings)".
- The expo dev client shows a welcome sheet on the first launch that only a real touch dismisses, it blocks synthetic `adb input tap`. Metro caches aggressively in /tmp/metro-cache, so a stale bundle can hide a code change; start it with `--clear` on a fresh port.
- The `write` tool reports type diagnostics against a stale snapshot in this build, so trust `npx tsc --noEmit` over the tool output.
- The app icons are generated by `sharp` from an svg with `node tools/generate-icons.js`, and `npx expo prebuild --clean --platform android` has to run again for the native resources to pick them up.
- The bottom tab bar is not an overlay, so a tab screen ends above it and must not add `tabBarHeight` or `insets.bottom` to its content padding. The tab bar already carries the bottom inset.
- The app was a TVS scooter companion and is now K Routes (com.kroutes.app): a route planner that avoids the ANSV photo detection cameras and the points the rider marks. The bluetooth layer, the garage, the dashboard, the ride tracker and the native module are gone. The PIN stays as an app lock, the live phone location and the saved routes stay.
- The google maps key is restricted to an android app in the google console. After the rename the key has to be re-restricted to `com.kroutes.app` and the sha1 `5e8f16062ea3cd2c4a0d547876baa6f38cabf625`, or the place search answers that the application is not authorized. The request carries the package name in the `X-Android-Package` header, so the constant in `src/config/geocoding.ts` is the one that has to follow the console.
- The official TVS Connect app accepts a `geo:` uri and an `ACTION_SEND` with text (both handled by its onboarding activity), so a destination can be handed to it from our app. It recomputes the route with Mappls, so a route that avoids the cameras cannot travel that way without patching that app.
- The official TVS Connect LATAM app (com.tvsm.connect.latam) is installed on the phone and its decompile lives in `.tmp/target`: its release build logs the frames it writes and the logcat of the phone (32 MB ring buffer) shows the uuids, the handles and the answers. The cluster of the rider spoke the letter protocol of the N112 (V + bike + $, X + signal, W + 17 every 2 s, H + clock, M + rider + $) with the writes to 5502 as a write with a response. The app no longer speaks it.
- The rider does the physical bike tests. Do not scan for, pair with or write to the cluster on your own; leave the build installed and let the rider run the ride.
- MapLibre RN 10.4.2 releases the camera tracking when the rider drags the map and never tells javascript, and while `followUserLocation` is true the Camera never applies its `centerCoordinate`. To take the camera back to the rider, remount the Camera with a changed key. Its `centerCoordinate` is `[lon, lat]` while the position of the app is `[lat, lon]`.
- On Android, `PointAnnotation` draws its child into a bitmap and adds it to the style, so the marker is invisible if the style is not loaded yet and the touch never reaches the child. Use `MarkerView` for every marker and keep every child inside the touchable, because a sibling drawn on top hides the icon.
- The rider wants every action on a map object in two taps: one tap opens a small menu with the options and every menu has a Cancel row. The touchable of a marker is the icon alone, not the row, and the name of the focused camera goes in a band and not on the marker.
- The turns of the route are gone: the app does not show or announce them. A saved route keeps the time the router gave plus the list of the times the rider took, and the estimate is the plain average of those times. The ride starts 10 m away from the point where the rider pressed start and ends 10 m from the destination, and only those two events are notified.
- The rider wants no dead code: after a change, delete what it leaves unused (unused exports, unused props, unused store actions, unreachable UI) instead of leaving it parked in the tree.
- The google cloud project is `maos-search` (number 947358802583, created 2026-11-08) on the open legacy billing account `012EF8-C37BE7-752A3D` (COP). Two api restricted keys: `busqueda` (android app com.kroutes.app + sha1 5e8f..., geocoding-backend + places) and `tiles` (tile.googleapis.com only, no application restriction and no daily quota, so the 3.225/day of `docs/FREE_SERVICES.md` is only arithmetic). routes.googleapis.com is not enabled and no key allows it.
- gcloud lives in `~/tools/google-cloud-sdk` (beta component installed) and is on the PATH from `tools/env.sh`; the rider account is owner of the project and billing.admin of the account. That legacy account answers 404 on costs, credits, budgets and associations, so the money is only in the console and the usage comes from cloud monitoring `serviceruntime.googleapis.com/api/request_count`.
- The app routes with valhalla for the route that goes around the cameras and the points of the rider (the "Around cameras" variant) and with the google Routes API (Compute Routes Pro, TRAFFIC_AWARE) for the "Main roads" variant, which never avoids anything. Both are computed in the same pass, so the variant switch does not ask again. The free caps are counted per sku and per month in the settings table (`googleUsage:<sku>:<YYYY-MM>`, the month of the pacific time) and the app falls back to valhalla and to the openfreemap liberty style at 95% of a cap.
- The pico y placa rules are bundled in `src/config/picoYPlaca.ts` (medellin by the first number for the motorcycles, cali by the last number and exempt for the motorcycles, bogota by the parity of the day, santa marta by the last number with the motorcycles not exempt); no city publishes an api for them. A moto plate is 3 letters, 2 numbers and a letter, so the number that counts is the last one before the letter. The rotation of a city changes twice a year, so the table has to be updated.
- The public valhalla instance refuses every route longer than 200 km (`Path distance exceeds the max distance limit`), so a long trip is computed by google and it does not avoid the cameras. The app says so with a banner.
- The arrival time is a motorcycle time: the scooter profile keeps its own time with a 1.15 factor inside the city, the google traffic aware car time keeps a 0.85 factor inside the city, and the valhalla car time without traffic takes a 1.1 factor. No engine publishes a motorcycle to car ratio, so the factors live in `src/services/eta.service.ts`.
- The installed apk on the phone is a release build with the js inside, not an expo dev client, so a code change only reaches the phone after `./android/gradlew -p android assembleRelease` with JDK 21 and an `adb install -r`.
