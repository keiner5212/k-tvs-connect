# Workspace notes

- RE toolchain is user-local: Ghidra in `~/tools/ghidra_12.1.4_PUBLIC` (pinned, the GhidraMCP 2.0 extension is built for it), jadx in `~/tools/jadx-1.5.6`, Android SDK in `~/Android/Sdk`, CLI tools in `~/.local/bin`. Load it with `. tools/env.sh`. jadx takes the heap through `JADX_OPTS=-Xmx6g`, and a long decompile runs in a docker container so it survives the session. MobSF runs in the container `mobsf` on `127.0.0.1:8000` (restart with `docker start mobsf`): upload, scan, then poll `report_json` with the hash.
- The host default is JDK 26, which gradle cannot use (the kotlin dsl cannot parse "26.0.1"). Build the apk with `JAVA_HOME=$HOME/.jabba/jdk/openjdk@21.0.2` and `ANDROID_HOME=$HOME/Android/Sdk`, then `./android/gradlew -p android assembleRelease`. The docker apk build caches gradle in the named volume `k-tvs-connect-gradle`, seeded from `~/.gradle`; mounting `~/.gradle` directly breaks the gradle daemon.
- The phone is connected over usb as RCUSTSEQTSK7RKSW (model 2602DPT53G). The MIUI phone can revoke INJECT_EVENTS for the adb shell, then `adb shell input tap` fails with exit 255; unlock it and enable "USB debugging (Security settings)".
- The expo dev client shows a welcome sheet on the first launch that only a real touch dismisses, it blocks synthetic `adb input tap`. Metro caches aggressively in /tmp/metro-cache, so a stale bundle can hide a code change; start it with `--clear` on a fresh port.
- The `write` tool reports type diagnostics against a stale snapshot in this build, so trust `npx tsc --noEmit` over the tool output.
- The app icons are generated by `sharp` from an svg in `.tmp/icongen/generate.js`, and `npx expo prebuild --clean` has to run again for the native resources to pick them up.
- The ride log is written by the native module to /sdcard/Android/data/com.ktvsconnect.app/files/ktvs-connect.log, so it survives the app being closed and can be pulled with adb. The Diagnostics screen in Settings shows and shares it.
- The app keeps the process alive with its own foreground service, of the `connectedDevice` type, with a wake lock, in the local module `modules/ktvs-cluster`.
- MIUI answers the battery optimisation intent with its own per app power screen, where the option the rider needs is "No restrictions".
- The bottom tab bar is not an overlay, so a tab screen ends above it and must not add `tabBarHeight` or `insets.bottom` to its content padding. The tab bar already carries the bottom inset.
- The cluster of the rider is the RTR 160 IoT V2 family (the original app calls it N112_V2 and pairs it with the U399C uuids). Its service is `00005500-d102-11e1-9b23-000240198212` with 5501 notify, 5502 write without response, 5503 write with response and 5504 read. It speaks the same 0x5B frames as the newer bikes, but the payload is xored with 0xEB instead of 0xEA, the rider name goes five times with 400 ms between them and the keepalive is 0x5B 0x4A every 2 s. The letter frames belong to the N112 v1 only.
- The original app pairs with the cluster before it writes to it and react-native-ble-plx has no bond api, so the pairing lives in the local native module `modules/ktvs-cluster`. Connected means the cluster sends a frame, not that the gatt link came up: a device that answers the connect but has no bike service is not a bike.
- On the real cluster every write with response to 5503 is refused by the gatt stack (CharacteristicWriteFailed), so the frame bytes never reached the cluster and the protocol is still untested. The app logs the android gatt status and the att error of each write, and it opens the link again after the pairing because android has to bring the encryption up on a fresh connection.
- The rider does the physical bike tests. Do not scan for, pair with or write to the cluster on your own; leave the build installed and let the rider run the ride.
- The public protocol docs of the other family (service 5456534D-..., frames 0x5A/0x5B, keepalive 0x4A every 2 s) are in github.com/athulkrishna2015/TVSRideCompanion, itvs-connect and TITANHACKY/ntorq-open-connect; they contradict each other on the checksum and the endianness of what the app writes, so the decompiled original wins.
- The cluster generates a pass key and shows it on its own display; the rider types that code in the app. The android pairing dialog does the same job. Never tell the rider a fixed code: 222333 comes from a log line of the original app and is not the code of the cluster.
- MapLibre RN 10.4.2 releases the camera tracking when the rider drags the map and never tells javascript, and while `followUserLocation` is true the Camera never applies its `centerCoordinate`. To take the camera back to the rider, remount the Camera with a changed key. Its `centerCoordinate` is `[lon, lat]` while the position of the app is `[lat, lon]`.
- On Android, `PointAnnotation` draws its child into a bitmap and adds it to the style, so the marker is invisible if the style is not loaded yet and the touch never reaches the child. Use `MarkerView` for every marker and keep every child inside the touchable, because a sibling drawn on top hides the icon.
- The rider wants every action on a map object in two taps: one tap opens a small menu with the options and every menu has a Cancel row. The touchable of a marker is the icon alone, not the row, and the name of the focused camera goes in a band and not on the marker.
